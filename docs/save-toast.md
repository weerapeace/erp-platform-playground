# apiSave — มาตรฐาน "กดบันทึกแล้วต้องรู้ผล"

`lib/save-toast.ts` · ใช้คู่กับ Toast กลาง (`components/toast`)

## ปัญหาที่แก้

หลายหน้าในระบบเคยยิงคำสั่งบันทึกแบบ **fire-and-forget**:

```ts
apiFetch("/api/…", { method: "PATCH", … }).catch(() => {});   // ❌ พังเงียบ
```

ถ้าเซิร์ฟเวอร์ปฏิเสธ (ไม่มีสิทธิ์ / ข้อมูลผิด / เน็ตหลุด) **ผู้ใช้ไม่รู้เลย** — กดปุ่มแล้วเหมือนบันทึกสำเร็จ
แต่ของจริงไม่ถูกบันทึก กลับมาดูอีกทีค่าหาย แล้วโทษว่า "ระบบไม่เก็บค่า"

## วิธีใช้

```ts
const toast = useToast();

const r = await apiSave(
  toast,
  "/api/bom/components",
  { body: { sku_id, fabric_width_cm: 160 } },              // method เริ่มต้น = PATCH
  { ok: "บันทึกหน้ากว้างกลับเข้า SKU แล้ว", fail: "บันทึกหน้ากว้างไม่สำเร็จ" },
);
if (!r.ok) return;        // ไม่สำเร็จ — toast แดงเด้งให้แล้ว พร้อมเหตุผลจากเซิร์ฟเวอร์
// สำเร็จ → toast เขียวเด้งแล้ว, ใช้ r.data ต่อได้
```

| พารามิเตอร์ | ความหมาย |
|---|---|
| `init.method` | ค่าเริ่มต้น `PATCH` (การบันทึกส่วนใหญ่คือแก้ของเดิม) |
| `init.body` | ใส่ object ได้เลย — แปลง JSON + ใส่ `Content-Type` ให้อัตโนมัติ |
| `opts.ok` / `opts.fail` | ข้อความ toast (เขียน**เป็นภาษาคน** บอกว่าบันทึก "อะไร" ไม่ใช่แค่ "สำเร็จ") |
| `opts.quiet` | `true` = ไม่เด้ง toast (บันทึกอัตโนมัติเบื้องหลัง) แต่ยังคืนผลให้เช็กเอง |

## กติกา

1. **ทุกปุ่มที่ผู้ใช้กดเองแล้วมีการเขียนข้อมูล ต้องเด้งผล** — ห้าม `.catch(() => {})` เฉย ๆ
2. ข้อความสำเร็จควรบอกว่าบันทึกอะไรไปที่ไหน เช่น
   `ตั้งชนิดของ RCY125-19 เป็น "ผ้า" แล้ว` ดีกว่า `บันทึกแล้ว`
3. ข้อความพลาดไม่ต้องแปลง error ดิบเอง — `apiSave` ต่อท้ายเหตุผลจากเซิร์ฟเวอร์ให้แล้ว
   (401 = ไม่มีสิทธิ์ · 4xx/5xx = ข้อความจาก API · เน็ตหลุด = ข้อความ network)
4. การบันทึกที่ระบบทำให้เองเบื้องหลัง (auto-save ถี่ ๆ) ใช้ `quiet: true` ได้ แต่ต้องมีทางบอกผู้ใช้เมื่อพลาด

## ใช้แล้วที่ไหน

- `app/master/bom/line-editor.tsx` — บันทึกหน้ากว้าง / หน่วย / ชนิดวัตถุดิบ กลับไปที่ SKU
- `components/sku-price-modal` — บันทึกราคาต้นทุนกลับเข้าสินค้า
