# ตรวจความเร็ว (perf-check) — เครื่องมือวัด + ผู้ตรวจรายวัน

> ภาษาคน: มีเครื่องวัดความเร็วอัตโนมัติ 2 ตัว ใช้กติกาเดียวกัน
> 1. **สคริปต์ `npm run perf-check`** — Claude รันหลัง deploy กับหน้าที่เพิ่งแก้ ได้ผลไม่กี่บรรทัด "ปกติ / ช้าลง X%"
> 2. **ผู้ตรวจความเร็ว (ทุกคืน 04:00)** — วัดหน้าหลัก + คำสั่งฐานข้อมูล แล้วเตือนแอดมินเมื่อช้าลง (ไม่ใช้ token ของ Claude)

เริ่มใช้ 2026-11-07 (เจ้าของเลือกเฟส 1+2) · กติกา/เกณฑ์อยู่ที่ `lib/perf-check.ts` ที่เดียว

## ใช้ทำอะไร / เมื่อไหร่

- **ทุกครั้งหลัง deploy งานที่แตะหน้าเว็บ** (CLAUDE.md ข้อ 46 Step 7 ชั้นที่ 5) → `npm run perf-check -- --changed`
- อยากรู้ว่าหน้าไหนหนัก → `npm run perf-check -- --key --verbose`
- สงสัยว่าฐานข้อมูลช้าลง → `npm run perf-check -- --db`

**ห้ามใช้แทน:** การวัดหน้าที่ต้องล็อกอินจริง (ดูข้อจำกัด) · การวัดบนเครื่อง dev แล้วเทียบค่าฐาน (`--url` ไม่เทียบ/ไม่จด)

## คำสั่ง

```
npm run perf-check -- --changed                 หน้าที่กระทบจากไฟล์ใน commit ล่าสุด + ที่ยังไม่ commit
npm run perf-check -- --changed --base <ref>    เทียบไฟล์ตั้งแต่ ref นี้ (เช่น หลาย commit)
npm run perf-check -- /purchasing /tasks        ระบุหน้า
npm run perf-check -- components/x/index.tsx    ระบุไฟล์ → หาหน้าที่ใช้ไฟล์นี้ (ไล่ด้วย where-used)
npm run perf-check -- --key                     หน้าหลัก 14 หน้า (ชุดเดียวกับผู้ตรวจรายวัน)
  --db        คำสั่งฐานข้อมูลที่ช้าขึ้นตั้งแต่รอบตรวจรายวันล่าสุด (ดูอย่างเดียว ไม่ขยับรอบ)
  --accept    ยอมรับค่าที่วัดได้เป็นค่าฐานใหม่ — ใช้เมื่อเจ้าของตกลงแล้วเท่านั้น
  --no-wait   ไม่รอพ้นช่วงหลัง deploy · --no-save ไม่จดค่าฐาน · --verbose ทุกหน้า · --json เครื่องอ่าน
  --url <base> วัดที่อื่น (เช่น dev) — ไม่เทียบ/ไม่จดค่าฐาน
```

⚠️ สคริปต์อาจรอ deploy + 3 นาทีก่อนวัด → ให้ Bash timeout 10 นาที (600000) หรือรันเบื้องหลัง · ต้องมี `.env.local` (กุญแจฐานข้อมูล) ไม่มี = วัดอย่างเดียว เทียบไม่ได้ · Node 22.18+

ตัวอย่างผล (ที่ Claude อ่าน):
```
⚡ perf-check · วัด 3 รายการ · ระบบปกติ (ping 0.14s) · ✅ 2 · ⚠️ 1
⚠️ /tasks  โค้ด 690KB (เดิม 531KB) · ตอบ 0.29s (เดิม 0.28s) — โค้ดโต 531KB→690KB (+30%) — น่าจะเพิ่งดึงของหนักเข้ามา
✅ ปกติ: /purchasing, /apps
→ ช้าลง/โตเกินเกณฑ์: หาสาเหตุแล้วแก้ ถ้าตั้งใจให้หนักขึ้น บอกเจ้าของก่อน (เจ้าของตกลงแล้วจึงรันซ้ำด้วย --accept)
```
exit 0 = ปกติ/ข้าม · 1 = มีหน้าช้าลงหรือโตเกินเกณฑ์ · 2 = deploy ล้ม/ใช้งานผิด

## วัดอะไร ยังไง

1. **รอพ้นช่วงหลัง deploy** — ถาม GitHub (gh) ว่า Vercel deploy ล่าสุดของ `feat/host-portable` เสร็จเมื่อไหร่ → รอให้พ้น 3 นาที (ฐานข้อมูลช้าทั้งระบบ ~2 นาทีหลัง deploy) · deploy ล้ม = หยุด
2. **เช็กสุขภาพระบบ** — `/api/ping` (ไม่แตะฐานข้อมูล) อุ่น 1 + วัด 3 ค่ากลาง · เกิน 0.6 วิ = "ระบบช้าทั้งก้อน" → ไม่ตัดสินเวลารอบนี้ (ขนาดโค้ดยังตัดสินได้)
3. **วัดทีละหน้า** (กันแย่งกันเอง) — เวลาตอบ: อุ่น 1 + วัด 5 ค่ากลาง · ขนาดโค้ด: รวม chunk JS ทุกตัวที่ HTML อ้าง แล้วบีบอัด brotli เอง (ใกล้เคียงขนาดดาวน์โหลดจริง — เว็บไม่บอกขนาดไฟล์บีบอัด)
4. **เทียบค่าฐาน** ใน `ui_config` key `perf_baseline:<path>` (1 แถวต่อหน้า ใช้ร่วมทุกเซสชัน/ทุกเครื่อง/ผู้ตรวจรายวัน)
   - ค่าฐาน = ค่ากลางของ 7 ครั้งล่าสุดที่ปกติ · ครั้งที่ช้าลงไม่ถูกจด (กันช้าแล้วกลายเป็นเรื่องปกติ) จนกว่าจะ `--accept`
   - เวลาตอบแยกที่วัด: `local` (เครื่องในไทย) / `cron` (Vercel โตเกียว) · ขนาดโค้ดใช้ร่วม

## เกณฑ์ (แก้ที่ `PERF_LIMITS` ใน lib/perf-check.ts)

| เรื่อง | ⚠️ เตือน | 🐢 ช้าผิดปกติ |
|---|---|---|
| เวลาตอบ | ช้ากว่าค่าฐาน > 50% **และ** ช้าลง > 0.15 วิ | หน้า > 1 วิ · API > 1.5 วิ (ถึงไม่มีค่าฐาน) |
| ขนาดโค้ดต่อหน้า | โต > 10% หรือ > 50KB · เกินเพดาน 700KB | — |
| คำสั่งฐานข้อมูล (รายวัน) | เฉลี่ย ≥ 0.5 วิ และเรียก ≥ 20 ครั้ง + (คำสั่งใหม่ หรือช้ากว่าเดิม ≥ 50%) | — |
| ระบบทั้งก้อน | ping > 0.6 วิ → ไม่ตัดสินเวลา วัดใหม่ทีหลัง | |

ค่าตั้งต้นที่วัดได้ 2026-11-07 (บีบอัด): /tasks ~531KB · /purchasing ~494KB · /master/design-dashboard ~436KB · /admin/plugins ~378KB · HTML ตอบ 0.04-0.3 วิ

## ผู้ตรวจความเร็วรายวัน — `/api/cron/perf-watch`

- vercel.json `0 21 * * *` (04:00 ไทย) · ลงทะเบียนออฟฟิศทีม AI id `perf-watch` (ห้องศูนย์ควบคุม) · จดรอบด้วย `recordWorkerRun`
- วัด: หน้าหลัก `PERF_KEY_PAGES` (14) + หน้าที่คนเปิดบ่อยสุด 7 วันจาก `page_view_daily` (6) · ค่าฐานแหล่ง `cron`
- ฐานข้อมูล: RPC `erp_perf_query_delta(p_commit:=true)` — migration `202611210100_perf_query_watch.sql`
  - pg_stat_statements เป็นยอดสะสม → เก็บภาพยอดรวมในตาราง `perf_query_snapshot` (ตัวเลขล้วน ไม่มีข้อความคำสั่ง) แล้วคิดส่วนต่างรอบถัดไป
  - นับเฉพาะคำสั่งของแอป (service_role / authenticated / anon) · รอบแรกเก็บภาพอย่างเดียว ไม่เตือน

- ช้าลง → กระดิ่ง `perf.regression` ตามกฎแจ้งเตือน (ตั้งต้นแอดมิน · แก้ที่แท็บแจ้งเตือน /master/flow-map) วันละครั้ง · ลิงก์ไป /master/ai-office
- ผลเต็มรอบล่าสุด: `ui_config` key `perf_watch_report` (หน้า + เหตุผล + คำสั่งฐานข้อมูลที่ช้าขึ้น)
- แอดมิน (ai_office.view) เรียก GET เองได้ = ดูผลอย่างเดียว (ไม่เตือน ไม่จด ไม่ขยับรอบ)

## ข้อจำกัด

- **หน้าที่ต้องล็อกอิน**: วัดได้แค่ "เปลือกหน้า + ขนาดโค้ด" — ข้อมูลที่หน้าดึงหลังล็อกอินวัดจากข้างนอกไม่ได้ (API ตอบ 401 เร็วเสมอ ไม่มีความหมาย → ข้าม) · ฝั่งนี้ดูจากคำสั่งฐานข้อมูลในรายงานรายวันแทน · ถ้าอยากได้เวลาที่ผู้ใช้จริงรอ = เฟส 3 (วัดผ่าน apiFetch กลาง — ยังไม่ทำ ต้องขออนุมัติตารางใหม่)
- chunk ที่โหลดทีหลัง (เปิดป๊อป/แท็บ) ไม่ถูกนับ — นับเฉพาะที่โหลดตอนเปิดหน้า
- หน้าที่มีช่องพารามิเตอร์ (`/x/[id]`) วัดตรงไม่ได้ → ข้าม
- แก้ของกลางที่ใช้ > 30 หน้า → วัดหน้าหลัก 14 หน้าแทน (ไม่ไล่ทุกหน้า)
- คำสั่งฐานข้อมูลบอกได้ว่า "ตาราง/ฟังก์ชันไหน" แต่ไม่บอกว่าหน้าไหนเรียก

## สิทธิ์ / audit

- ไม่แตะข้อมูลธุรกิจ · เขียนแค่ `ui_config` (ค่าฐาน + รายงาน) และ `perf_query_snapshot` · ไม่ต้องลง audit (เป็นค่าวัดของระบบ ไม่ใช่การแก้ข้อมูลโดยคน)
- สคริปต์ใช้กุญแจ service role จาก `.env.local` บนเครื่อง (แพทเทิร์นเดียวกับสคริปต์ backfill อื่น) · ไม่ใช้รหัสผ่านผู้ใช้
